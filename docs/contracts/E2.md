# hookrelay — E2 Contract: Delivery pipeline

Read together with [`docs/CONTRACT.md`](../CONTRACT.md) and
[`docs/contracts/E1.md`](E1.md). Where they differ, this file wins for E2.

## 1. Goal and scope

At the end of E2, every `PENDING` delivery created in E1 is actually **sent**: an
HTTP `POST` with the event payload goes to the endpoint URL, and the outcome is
recorded on the delivery and in a new attempt history.

**Out of scope:** retries, backoff and DLQ (E3). In E2 a failed attempt is final
(`FAILED`, no next attempt). Also out of scope: request signing, SSRF protection
and API auth (E4), metrics and tracing (E5), replay (E6).

## 2. Design (PostgreSQL is the source of truth, RabbitMQ distributes work)

```
POST /events ──tx──▶ deliveries (PENDING)
                          │  every poll-interval
                          ▼
                  DeliveryPoller ── claims due rows (FOR UPDATE SKIP LOCKED),
                          │         sets locked_until, bumps version
                          ▼
            RabbitMQ  exchange hookrelay.deliveries ─▶ queue hookrelay.deliveries.dispatch
                          │   message {deliveryId, version}
                          ▼
                  DeliveryWorker ── claim(id, version) ─▶ HTTP POST ─▶ record result + attempt
```

### 2.1 Poller (`DeliveryPoller`)

- Runs every `hookrelay.dispatch.poll-interval` (`@Scheduled`, fixed delay) when
  `hookrelay.dispatch.enabled=true`.
- In **one transaction**:
  1. select up to `batch-size` ids with
     `status = 'PENDING' AND next_attempt_at <= now AND (locked_until IS NULL OR locked_until < now)`
     `ORDER BY next_attempt_at` … `FOR UPDATE SKIP LOCKED` (native query);
  2. for each: `locked_until = now + lease`, `version = version + 1`,
     `updated_at = now`;
  3. publish one message per delivery `{"deliveryId": "<uuid>", "version": <new version>}`
     and wait for **publisher confirms**. If a publish fails, throw, so the
     transaction rolls back and the rows are picked up by the next poll.
- `SKIP LOCKED` makes several app instances safe to run at once.

### 2.2 Worker (`DeliveryWorker`, `@RabbitListener`)

For each message:

1. **Claim** (own short transaction, native update):
   ```sql
   UPDATE deliveries
      SET locked_until = :now + lease, attempt_count = attempt_count + 1,
          version = version + 1, updated_at = :now
    WHERE id = :id AND version = :version AND status = 'PENDING'
   RETURNING attempt_count, version
   ```
   0 rows → stale or duplicate message: log at DEBUG, ack and stop.
2. Load the event and the endpoint. If the endpoint is disabled or soft-deleted,
   record the result as `FAILED` with `last_error` `"Endpoint disabled"` or
   `"Endpoint deleted"`, and do **not** send. Still write an attempt row with
   `response_status = null` and `duration_ms = 0`.
3. **Send** (outside any transaction): see §2.3.
4. **Record** (own transaction): insert the `delivery_attempts` row, then
   ```sql
   UPDATE deliveries
      SET status = :status, last_attempt_at = :startedAt,
          last_response_status = :code, last_error = :error,
          locked_until = NULL, next_attempt_at = NULL,
          version = version + 1, updated_at = :now
    WHERE id = :id AND version = :claimedVersion
   ```
   `status` is `SUCCEEDED` on 2xx, otherwise `FAILED`. 0 rows means the lease
   expired and someone else took over: log at WARN and keep the attempt row.
   Update the row only, never the attempt.
- Exceptions (for example, the DB is down) are **not** requeued
  (`spring.rabbitmq.listener.simple.default-requeue-rejected: false`). The row is
  still `PENDING`, so the poller republishes it after the lease expires.

**Guarantee:** at-least-once. One claim succeeds per published version, so
duplicate or stale messages never send twice. A second send can only happen
when an attempt outlives its `lease`. Receivers dedupe on
`Hookrelay-Delivery-Id`.

### 2.3 HTTP request (`WebhookSender`)

- Spring `RestClient` on `JdkClientHttpRequestFactory`. JDK `HttpClient` with
  `connect-timeout`, `Redirect.NEVER`, HTTP/1.1. `request-timeout` is the read
  timeout.
- `POST <endpoint.url>`, body = the event `payload` serialized as JSON.
- Headers:

  | Header | Value |
  |--------|-------|
  | `Content-Type` | `application/json` |
  | `User-Agent` | `hookrelay/<app version>` (`hookrelay/0.0.1-SNAPSHOT` is fine) |
  | `Hookrelay-Delivery-Id` | delivery UUID |
  | `Hookrelay-Event-Id` | event UUID |
  | `Hookrelay-Event-Type` | event type |
  | `Hookrelay-Attempt` | attempt number (1-based) |
  | `Hookrelay-Timestamp` | send time, Unix epoch seconds |

- Outcome:
  - Any 2xx → `SUCCEEDED`.
  - Any other status, 3xx included → `FAILED`, `last_error = "HTTP <code>"`.
  - I/O error or timeout → `FAILED`, `response_status = null`,
    `last_error = "<ExceptionSimpleName>: <message>"`, truncated to 2000 chars.
- Response bodies are read and discarded, never stored.

## 3. Schema (Flyway `V2__dispatch.sql`, exactly)

```sql
ALTER TABLE deliveries ADD COLUMN locked_until TIMESTAMPTZ;

CREATE INDEX idx_deliveries_due ON deliveries (next_attempt_at) WHERE status = 'PENDING';

CREATE TABLE delivery_attempts (
    id              UUID PRIMARY KEY,
    delivery_id     UUID        NOT NULL REFERENCES deliveries (id),
    attempt_number  INTEGER     NOT NULL,
    outcome         VARCHAR(20) NOT NULL,
    started_at      TIMESTAMPTZ NOT NULL,
    duration_ms     BIGINT      NOT NULL,
    response_status INTEGER,
    error           VARCHAR(2000),
    CONSTRAINT uq_delivery_attempts_number UNIQUE (delivery_id, attempt_number),
    CONSTRAINT ck_delivery_attempts_outcome CHECK (outcome IN ('SUCCEEDED', 'FAILED'))
);
```

Map `locked_until` on `Delivery` (`lockedUntil`, not exposed in the API) and add
the entity `DeliveryAttempt` with `DeliveryAttemptRepository`.

## 5. RabbitMQ topology (declared by the app as `Declarables`)

| Kind | Name | Properties |
|------|------|-----------|
| Direct exchange | `hookrelay.deliveries` | durable |
| Queue | `hookrelay.deliveries.dispatch` | durable |
| Binding | queue ← exchange | routing key `dispatch` |

- Messages are JSON (`Jackson2JsonMessageConverter`) and persistent.
- Listener prefetch 10, concurrency `hookrelay.dispatch.consumers`.
- `spring.rabbitmq.publisher-confirm-type: correlated` (or `simple`). The poller
  must not commit before its publishes are confirmed.

## 6. Configuration

`@ConfigurationProperties("hookrelay.dispatch")` record `DispatchProperties`,
validated (`@Validated`). Each property can be set by environment variable
through relaxed binding, so no new entries are needed in `application.yml`
beyond the defaults:

| Property | Env var | Default |
|----------|---------|---------|
| `enabled` | `HOOKRELAY_DISPATCH_ENABLED` | `true` |
| `poll-interval` | `HOOKRELAY_DISPATCH_POLL_INTERVAL` | `1s` |
| `batch-size` | `HOOKRELAY_DISPATCH_BATCH_SIZE` | `100` |
| `lease` | `HOOKRELAY_DISPATCH_LEASE` | `60s` (must be > connect + request timeout) |
| `connect-timeout` | `HOOKRELAY_DISPATCH_CONNECT_TIMEOUT` | `5s` |
| `request-timeout` | `HOOKRELAY_DISPATCH_REQUEST_TIMEOUT` | `10s` |
| `consumers` | `HOOKRELAY_DISPATCH_CONSUMERS` | `4` |

When `enabled=false`, neither the poller nor the listener runs (listener
`autoStartup=false`). Everything else, including the API, works as in E1.

## 7. Code layout

New package `io.github.joseferrao20.hookrelay.dispatch`: `DispatchProperties`,
`DispatchConfig` (topology, `RestClient`, scheduling enablement), `DeliveryMessage`
(record), `DeliveryPoller`, `DeliveryWorker`, `WebhookSender`, `SendResult`
(record). The claim and record SQL lives in `DeliveryRepository` as native
`@Modifying` queries, or in a small `DeliveryDispatchRepository` in `delivery`.
Package `delivery` also gets `DeliveryAttempt`, `DeliveryAttemptRepository`,
`DeliveryAttemptResponse` and the attempts endpoint in `DeliveryController`.

## 8. Tests (app)

- **No test may make network calls outside the test JVM and its containers.**
  Every test that is not about dispatch runs with
  `hookrelay.dispatch.enabled=false`. Set this in the shared test setup (for
  example `@SpringBootTest(properties=…)`, or a test `application-test.yml` with
  an active profile). Do **not** add `src/test/resources/application.yml`: it
  would shadow the main one.
- Add `org.wiremock:wiremock-standalone:3.13.2` (test) and use Awaitility (BOM
  managed) for async assertions.
- Dispatch integration tests (Testcontainers + WireMock) must cover:
  - 2xx → `SUCCEEDED`, `attempt_count = 1`, one attempt row, all `Hookrelay-*`
    headers present and correct, body equals payload;
  - 500 → `FAILED`, `last_response_status = 500`, `last_error = "HTTP 500"`;
  - a timeout (WireMock fixed delay > request-timeout, with short test timeouts)
    → `FAILED` with `response_status` null;
  - a 3xx is not followed and ends `FAILED`;
  - a disabled endpoint → `FAILED "Endpoint disabled"` and no HTTP request;
  - a stale or duplicate message (wrong version) → no HTTP request, no state
    change;
  - the poller publishes due deliveries only, skipping `locked_until` in the
    future and `next_attempt_at` in the future;
  - `GET /deliveries/{id}/attempts` (slice test + one integration assertion).
- `./gradlew build` stays green.

## 9. Webhook sink and smoke test (local-infra)

- `scripts/webhook-sink.py`: a stdlib-only Python 3 HTTP server.
  - It records every request made to any path other than `/received`
    (method, path, headers, body) in memory and answers `200`.
  - `GET /received` returns the recorded requests as a JSON array.
  - It listens on `0.0.0.0:${PORT:-8080}`.
- Compose service `webhook-sink` under a **new profile `sink`**: image
  `python:3.12-alpine`, mounts `scripts/webhook-sink.py` read-only and runs it,
  healthcheck on `/received`, host port `${SINK_PORT:-8090}:8080`. Add
  `SINK_PORT=8090` to `.env.example`.
- `scripts/smoke-test.sh [BASE_URL] [SINK_URL]`. The defaults are
  `http://localhost:8080` and `http://localhost:8090`.
  - Keep E1 steps 1–6, but create the endpoint with URL
    `http://webhook-sink:8080/hooks` (the in-network address seen by the app
    container). The POST response must still show the delivery `PENDING`.
  - Do not assert the status in later reads, because dispatch may already have
    happened.
  - New steps, run before the endpoint is deleted:
    - poll `GET /api/v1/deliveries/{id}` until `SUCCEEDED` (max 30 s);
    - check that `GET /api/v1/deliveries/{id}/attempts` has 1 attempt with
      outcome `SUCCEEDED`;
    - check that `SINK_URL/received` contains a request whose
      `Hookrelay-Delivery-Id` header equals the delivery id, with a body equal
      to the payload.
- Makefile: `up-all` (`docker compose --profile app --profile sink up -d --build --wait`),
  `down-all` (`docker compose --profile app --profile sink down -v`). `smoke`
  stays as is.
