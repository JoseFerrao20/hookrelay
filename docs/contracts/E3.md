# hookrelay — E3 Contract: Retries, backoff & DLQ

Read together with [`docs/CONTRACT.md`](../CONTRACT.md), [`E1.md`](E1.md) and
[`E2.md`](E2.md). Where they differ, this file wins for E3.

## 1. Goal and scope

At the end of E3:

- A failed attempt is **retried with exponential backoff and jitter** until it
  succeeds or reaches `max-attempts`.
- Exhausted, permanently rejected and undeliverable deliveries end as **`DEAD`**.
- Messages that the worker cannot process are parked in a **RabbitMQ
  dead-letter queue** instead of being dropped.

**Out of scope:** manual retry/replay of `DEAD` deliveries and DLQ redrive (E6),
signing/SSRF/auth (E4), metrics/alerts on DEAD counts (E5).

## 2. Delivery state machine

```
            ┌──────── retryable failure, attempts left ────────┐
            ▼                                                   │
PENDING ──attempt──▶ SUCCEEDED (terminal)                      │
   │                                                            │
   └──attempt fails──▶ FAILED (next_attempt_at = now + backoff) ┘
                         │
                         └── no attempts left / non-retryable ──▶ DEAD (terminal)
```

- `PENDING`: never attempted. `FAILED`: last attempt failed **and a retry is
  scheduled** (`next_attempt_at` not null). `SUCCEEDED` and `DEAD` are terminal,
  with `next_attempt_at = NULL`.
- The poller (E2 §2.1) and the worker claim (E2 §2.2) now accept
  `status IN ('PENDING', 'FAILED')`. Everything else about leases, versions and
  publish-after-commit is unchanged.
- **Outcome after an attempt** (worker "record" step):

  | Result of attempt N | New status | `next_attempt_at` |
  |---------------------|-----------|-------------------|
  | 2xx | `SUCCEEDED` | `NULL` |
  | `410 Gone` | `DEAD` | `NULL` |
  | any other failure, `N < max-attempts` | `FAILED` | `now + delay(N)` |
  | any other failure, `N >= max-attempts` | `DEAD` | `NULL` |
  | endpoint soft-deleted or disabled (no HTTP sent) | `DEAD` | `NULL` |

  "Any other failure" means any non-2xx status (3xx and 4xx included) and any
  I/O error or timeout. Receivers that are briefly misconfigured, e.g. returning
  401 during a key rotation, therefore still get retried. `410` is the receiver
  saying "never send this again".
- The attempt row (E2 §3) is written exactly as in E2. Its outcome stays
  `SUCCEEDED`/`FAILED`; only the delivery becomes `DEAD`.
- For a `DEAD` delivery, `last_error` explains why:
  - after exhausting retries, it keeps the last attempt's error, suffixed with
    ` (gave up after N attempts)`;
  - on `410`: `HTTP 410 (gone)`;
  - for an endpoint that is deleted or disabled: `Endpoint deleted` or
    `Endpoint disabled`.

## 3. Backoff policy (`RetryPolicy`, pure and unit-tested)

`delay(N)` is the wait after failed attempt `N` (1-based):

```
base(N)  = min(max-delay, initial-delay × multiplier^(N-1))
delay(N) = base(N) × (1 + U(-jitter, +jitter)), clamped to [0, max-delay]
```

- **`Retry-After`:** for responses `429` and `503` with a valid `Retry-After`
  (delta-seconds or HTTP-date), use `max(delay(N), retryAfter)`, capped at
  `max-delay`. A missing or invalid header falls back to `delay(N)`.
- **Randomness:** inject the random source (or `jitter = 0` in tests) so tests
  are deterministic.
- **Defaults:** `max-attempts = 10`, `initial-delay = 30s`, `multiplier = 2.0`,
  `max-delay = 6h`, `jitter = 0.2`. The nominal schedule is
  30s, 1m, 2m, 4m, 8m, 16m, 32m, 64m, 128m, about 4.3 h in total.

## 4. Configuration

Add `@ConfigurationProperties("hookrelay.retry")` record `RetryProperties`
(`@Validated`). Both env var forms bind (`HOOKRELAY_RETRY_INITIAL_DELAY` and
`HOOKRELAY_RETRY_INITIALDELAY`); docs use the underscore form.

| Property | Env var | Default | Validation |
|----------|---------|---------|------------|
| `max-attempts` | `HOOKRELAY_RETRY_MAX_ATTEMPTS` | `10` | 1..100 |
| `initial-delay` | `HOOKRELAY_RETRY_INITIAL_DELAY` | `30s` | > 0 |
| `multiplier` | `HOOKRELAY_RETRY_MULTIPLIER` | `2.0` | ≥ 1.0 |
| `max-delay` | `HOOKRELAY_RETRY_MAX_DELAY` | `6h` | ≥ initial-delay |
| `jitter` | `HOOKRELAY_RETRY_JITTER` | `0.2` | 0.0..1.0 |

## 5. Schema (Flyway `V3__retries.sql`, exactly)

```sql
-- E2 left terminal failures as FAILED with no next attempt; in E3 that state is DEAD.
UPDATE deliveries
   SET status = 'DEAD', updated_at = now()
 WHERE status = 'FAILED' AND next_attempt_at IS NULL;

DROP INDEX idx_deliveries_due;
CREATE INDEX idx_deliveries_due ON deliveries (next_attempt_at)
    WHERE status IN ('PENDING', 'FAILED');
```

No new columns. The `version` and `locked_until` columns from E1/E2 are reused.

## 6. RabbitMQ: dead-letter queue

The existing queue cannot gain `x-dead-letter-exchange` in place, because
redeclaring it with new arguments fails with `PRECONDITION_FAILED`. So E3 moves
to a new work queue and removes the old one.

| Kind | Name | Properties |
|------|------|-----------|
| Direct exchange | `hookrelay.deliveries` | unchanged |
| Queue | `hookrelay.deliveries.work` | durable, `x-dead-letter-exchange = hookrelay.deliveries.dlx`, `x-dead-letter-routing-key = dead` |
| Binding | work ← `hookrelay.deliveries` | routing key `dispatch` (unchanged; the poller code does not change) |
| Direct exchange | `hookrelay.deliveries.dlx` | durable |
| Queue | `hookrelay.deliveries.dlq` | durable |
| Binding | dlq ← dlx | routing key `dead` |

- **Legacy cleanup:** on startup the app deletes the E2 queue
  `hookrelay.deliveries.dispatch` if it exists (`AmqpAdmin.deleteQueue`, which is
  idempotent). Otherwise its binding would keep copying every message into a
  queue that nothing consumes. Log once at INFO when a queue was actually
  deleted. Losing its in-flight messages is safe, because the poller republishes
  after the lease expires.
- **What lands in the DLQ:** with `default-requeue-rejected: false` (E2), any
  message the listener rejects — an exception in the worker, or a message that
  cannot be converted (poison) — goes to `hookrelay.deliveries.dlq`.
  - Nothing consumes the DLQ in E3. It is for inspection; redrive comes in E6.
  - The delivery row is still recovered by the poller after the lease expires,
    so the DLQ never holds the only copy of work.
- **Business outcomes do not go to the DLQ.** A `DEAD` delivery is recorded in
  Postgres only (§2).

## 7. API

No new endpoints. Existing reads already expose what is needed:

- `status` can now be `DEAD`.
- `nextAttemptAt` shows the scheduled retry.
- `attemptCount` and `/attempts` show the history.

The `GET /api/v1/deliveries?status=` filter must accept `DEAD`, which the E1
enum already allows.

## 8. Code layout

In `dispatch`:

- add `RetryProperties`, `RetryPolicy` and `RetryDecision`, a record with
  `status`, `nextAttemptAt` and `lastError`;
- extend `SendResult` with an optional `retryAfter` (`Duration`, parsed by
  `WebhookSender` for 429/503);
- `DeliveryWorker` asks `RetryPolicy` for the decision and passes it to the
  record query;
- `DispatchConfig` declares the §6 topology and the legacy-queue cleanup.

In `DeliveryRepository`:

- the record query takes `status` and `next_attempt_at` as parameters;
- the lease and claim queries accept `PENDING` and `FAILED`.

## 9. Tests (app)

- **`RetryPolicyTest` (unit, no Spring):**
  - the nominal schedule with `jitter = 0`;
  - the `max-delay` cap;
  - jitter bounds over many samples;
  - `Retry-After` in seconds and as an HTTP-date, plus invalid values;
  - the `410` and exhausted cases;
  - `max-attempts = 1` means no retries.
- **Integration tests** (Testcontainers + WireMock, short delays such as
  `initial-delay = 200ms`, `max-delay = 1s`, `jitter = 0`):
  - 500, 500, 200 → `SUCCEEDED` after 3 attempts; attempts 1–2 `FAILED`, 3
    `SUCCEEDED`;
  - always 500 with `max-attempts = 3` → `DEAD` after exactly 3 attempts, with
    `last_error` ending in `(gave up after 3 attempts)`;
  - 410 → `DEAD` after 1 attempt;
  - 429 with `Retry-After: 1` → the next attempt is not earlier than 1 s after
    the first;
  - while waiting, a `FAILED` row has `next_attempt_at` set and the poller does
    not pick it before that time;
  - deleted endpoint → `DEAD "Endpoint deleted"`;
  - a message published straight to the exchange with a body that cannot be
    converted ends in `hookrelay.deliveries.dlq` (use `RabbitAdmin`/
    `getQueueInfo`);
  - the legacy queue `hookrelay.deliveries.dispatch` is deleted at startup
    (declare it before the context starts, or check `getQueueInfo` returns
    null);
  - the V3 data migration turns a legacy `FAILED`/`NULL` row into `DEAD`. A
    Flyway test is optional; a repository-level check of the SQL is acceptable.
- Existing E2 tests are updated where they asserted a final `FAILED`. With the
  default `max-attempts` they now expect `FAILED` with a `next_attempt_at`, or
  they run with `max-attempts = 1` and expect `DEAD`.
- `./gradlew build` stays green.

## 10. Local infra and smoke test (local-infra)

- **`scripts/webhook-sink.py`** gets two deterministic routes, still stdlib
  only. Requests to both are recorded like any other.
  - `/status/<code>` answers with that status code.
  - `/flaky/<key>?fail=<n>` answers `500` for the first `n` requests per `key`,
    then `200`.
- **Compose `app` service** passes `HOOKRELAY_RETRY_MAX_ATTEMPTS`,
  `HOOKRELAY_RETRY_INITIAL_DELAY`, `HOOKRELAY_RETRY_MAX_DELAY` and
  `HOOKRELAY_RETRY_JITTER` through with `${VAR:-<default from §4>}`. Add them to
  `.env.example` with the defaults.
- **Makefile `up-all`** runs with fast retries for development:
  `HOOKRELAY_RETRY_INITIAL_DELAY=1s HOOKRELAY_RETRY_MAX_DELAY=5s HOOKRELAY_RETRY_JITTER=0`.
- **`scripts/smoke-test.sh`** keeps every E2 step and adds, before the cleanup
  step:
  1. An endpoint at `http://webhook-sink:8080/flaky/<random>?fail=2`. Post an
     event and wait (max 60 s) for the delivery to reach `SUCCEEDED` with
     exactly 3 attempts: `FAILED`, `FAILED`, `SUCCEEDED`.
  2. An endpoint at `http://webhook-sink:8080/status/410`. Post an event and
     wait (max 30 s) for `DEAD` with 1 attempt and `lastError` containing
     `410`.
  3. Delete both endpoints.
  - If step 1 times out, print a hint that the stack must run with fast retries
    (`make up-all`, or the env vars above).
